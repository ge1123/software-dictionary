已入帳卻來不及 ACK，重送會再加一次嗎？

本詞典的 .NET 實驗有一個帳戶，期初餘額為 0。發布端送出訊息 credit-17，內容要求入帳 250 個最小貨幣單位。消費者提交 PostgreSQL 交易後立刻退出，刻意把故障放在 COMMIT 與 RabbitMQ 的 ACK 之間。

為什麼只入帳一次？

processed_events.event_id 是主鍵。寫入新鍵時，RETURNING 產生一列，餘額更新才符合條件。相同鍵再次抵達時，ON CONFLICT DO NOTHING 傳回零列。事件登記和餘額更新使用同一筆交易，兩者一起提交或一起回滾。

看 PostgreSQL 的入帳條件 
WITH first_delivery AS (
    INSERT INTO processed_events (event_id) VALUES (@id)
    ON CONFLICT (event_id) DO NOTHING RETURNING event_id
)
UPDATE account SET balance_minor = balance_minor + @amount
WHERE account_id = 1 AND EXISTS (SELECT 1 FROM first_delivery)

@id 和 @amount 是 .NET 傳給 Npgsql 的參數。實驗預先建立帳戶 1，同一事件的每次投遞都使用相同 ID 與金額。

壞訊息去哪裡？

實驗接著送一筆 ID 為 malformed-1、內容只有左大括號的訊息。解析 JSON 失敗時，消費者回覆 BasicNack(requeue: false)。工作佇列已設定死信路由，驗收程式從 credits.dead 讀回相同 ID 和內容並確認收件。餘額仍為 250，已處理事件仍只有一筆。

自己重跑

在有 Docker Compose v2 的電腦，從詞典專案根目錄執行下列指令。每次會建立獨立的 Compose 專案，結束後清除該次容器和資料卷。

bash labs/rabbitmq-redelivery/run.sh

通過時最後一個消費者會印出 PASS redelivered=true; balance_minor=250; processed_events=1; DLQ=malformed-1。測試要求 broker 真正重送、資料庫餘額正確、兩個佇列都已讀完。

這份驗收涵蓋單一帳戶及同一 PostgreSQL 交易內的副作用。若處理動作還包括呼叫外部扣款 API，該呼叫要另外驗證自己的冪等機制。
